# Gerrit review output (gerrit-review.json)

Lustre reviews are posted to Gerrit, not emailed to a mailing list. Instead of
the plain-text `review-inline.txt`, produce a single JSON file,
`./gerrit-review.json`, in the current directory (never the prompt directory).
The file is a Gerrit `ReviewInput` body that can be POSTed to:

    POST /changes/{change-id}/revisions/{revision-id}/review

(the harness that runs the review fills in change-id/revision-id; you only
produce the JSON body).

Create `./gerrit-review.json` only when regressions/issues are found. The
content/phrasing rules below replace the mailing-list framing of
inline-template.md, but the *thinking* about what counts as an issue is
unchanged.

## ReviewInput structure

```json
{
  "tag": "autogenerated:ai-review",
  "message": "<short overall summary; 1-3 sentences of plain text>",
  "comments": {
    "<file path>": [
      {
        "line": <int, line in the patched (new) file>,
        "message": "<the review comment>",
        "unresolved": true
      }
    ]
  }
}
```

Field rules:
- `comments` is a map: key = file path **relative to the repo root, exactly as
  Gerrit stores it** (e.g. `lustre/osc/osc_request.c`), value = array of comment
  objects on that file.
- Each comment object:
  - `line`: 1-based line number in the **new** (post-patch) file — this is the
    `REVISION` side, which is the default. Use the line you actually read from
    the checked-out worktree (the worktree has the commit applied, so its line
    numbers match the revision Gerrit will display).
  - `range` (optional, preferred when the issue spans a region): object with
    `start_line`, `start_character`, `end_line`, `end_character` (0-based
    characters, 1-based lines, end exclusive of character). When you give a
    `range`, also set `line` to `range.end_line`.
  - `message`: the comment text (see phrasing rules below).
  - `unresolved`: `true` for anything you want a human to act on (all real
    findings). Use `false` only for pure informational notes.
  - `side`: omit for the new file. Use `"PARENT"` only to comment on a line that
    exists solely in the pre-patch file (rare).
  - `in_reply_to`: omit (we are not threading onto existing comments).
- `message` (top level): the **overall verdict**, plus any whole-patch
  observation that is not tied to a code line and is not a commit-message matter.
  - Default to a short one-liner, roughly one of: "Looks good." / "Mostly good,
    minor comments inline." / "Some concerns, see inline comments." /
    "Problematic, see inline comments."
  - Make it clear whether a refresh is actually warranted. Minor-only findings
    should read as "fine to land; optional nits for the next refresh", not as a
    request to re-spin (see "Review cycles are expensive" below).
  - Do **not** restate the individual inline comments here — their details live
    on their lines.
  - When there is a real whole-patch point — the change should be split into
    separate patches, the approach is wrong, it needs test coverage added ("this
    should add a test for X"), a show-stopper a reader must see first — put it
    here, and let it replace or extend the one-liner as the nature of the point
    warrants. A few sentences is fine when justified; still not a dump of the
    inline nits.
  - Commit-message matters do **not** go here — Fixes: tag, subject/component
    tag, body completeness, and Test-Parameters all belong on `/COMMIT_MSG`.
- `tag`: keep `"autogenerated:ai-review"` so the comments are clearly marked as
  machine-generated.
- **Labels / voting:** do NOT include a `labels` field by default. Leave the
  Code-Review vote to a human. (A wrapping pipeline may add a label; the review
  itself should not vote.)
- Do not invent other top-level fields.

### Commit message comments

To comment on the commit message, use the magic path `"/COMMIT_MSG"`.

Gerrit's `/COMMIT_MSG` pseudo-file has a 6-line generated header (`Parent:`,
`Author:`, `AuthorDate:`, `Commit:`, `CommitDate:`, blank), so the real commit
**subject is line 7**, and body lines follow. Account for this +6 offset when
anchoring to a specific commit-message line. If you are unsure of the exact
line, omit `line` to attach a file-level comment to the commit message instead.

**A missing `Fixes:` tag suggestion always goes on `/COMMIT_MSG`**, anchored to
the line where it should be inserted: the blank line directly **above the
`Signed-off-by:` / `Change-Id:` trailer block** (that is where the `Fixes:` line
belongs). Find the first trailer line in the commit message, apply the +6
header offset, and anchor the comment to the line just above it; put the exact
suggested `Fixes: <sha> ("subject")` line in the comment `message` so it can be
pasted in. If you can't pin the line precisely, anchor on the `Signed-off-by:`
line itself.

**A missing/insufficient `Test-Parameters:` line also goes on `/COMMIT_MSG`** —
this is a commit-message field, so it is a line comment there, anchored to the
existing `Test-Parameters:` line (if the ask is to expand it) or to the trailer
area where it should be added. Contrast this with "the patch should add an
actual test case for X", which is a whole-patch observation and goes in the
top-level `message`.

### Where whole-change observations go

Route by what the observation is about; never use a `/PATCHSET_LEVEL`
pseudo-file:

- **Commit-message matters → `/COMMIT_MSG`** (line comments): the `Fixes:` tag,
  the subject / component tag, body completeness/accuracy, and the
  `Test-Parameters:` line. Anchor each to the relevant commit-message line.
- **Other whole-patch observations → top-level `message`**: split the patch into
  separate changes, the overall approach is wrong, the patch should add a test
  case for the new behavior, a cross-cutting concern with no single home. These
  can expand the `message` beyond the one-line verdict.
- **Everything else → the real file line** it concerns.

## Phrasing rules (carried over from inline-template.md)

These still apply — Gerrit comments are read by the same maintainers:

- Comments are plain prose anchored to a line. Because the comment is already
  attached to the code, **do not quote the diff or use `> ` email quoting**, and
  **do not restate the line number in the text** — the anchor does that.
- Be factual and undramatic. Frame findings as questions, not accusations, and
  do not address the author personally.
  - not: "You leak the folio here." -> "Can this leak the folio if
    cl_page_find() fails?"
- Name the specific thing. Not "resource leak" but "does this leak `lock`?";
  not "possible overflow" but "can `idx` exceed `lsm_entry_count`?".
- Vary your phrasing; don't open every comment with "Does this code ...".
- Keep comments short. Use small plain-text code snippets or `funcA()->funcB()`
  call chains instead of dense paragraphs. Break a multi-sentence comment into
  short logical groups.
- No ALL-CAPS labels (no `REGRESSION:`, no `SYZKALLER-1:`). State the issue
  plainly. Gerrit renders limited markdown; a short ```code``` fence or a blank
  line between paragraphs is fine, but keep it minimal.
- For subjective/style findings (SR-* patterns, or Adilger-style nits from
  lustre-style.md), soften: "this isn't a bug, but ..." / "if the patch is
  refreshed, consider ...".
- Don't over-explain obvious copy/paste or forgotten-update mistakes; a one-line
  note is enough. Don't explain why a typo is bad — just point it out.
- Include every confirmed issue; never include findings you decided were false
  positives.
- Do not post a comment that repeats a point a human reviewer already made on
  the current patchset — that just adds noise. Existing review comments may only
  be carried into your output as an unaddressed prior-revision point, or with new
  evidence that advances a reviewer's open question (see review-core.md TASK 2
  step 3).

## Severity markers

Lustre reviewers prefix each comment with a severity/category marker. Use the
same convention so the comments read as familiar; start the comment `message`
with the marker. The topic guides (lustre-style.md, wire-protocol.md, tests.md,
lustre-utils.md, lustre-commit-message.md) tell you which marker fits each rule.

- **`(defect)`** — a real correctness / ABI / protocol / memory bug that
  introduces a new failure condition, with a concrete reachable path. Report as
  a regression; these justify a negative review. Never use it for a missing
  `Fixes:` tag, a commit-message gap, a kernel-doc/comment inaccuracy, or a
  style deviation — those are `(style)`/`(minor)`; mislabeling them as defects
  is a recurring complaint.
- **`(minor)`** — small optional improvement or code style issue that may result
  in a defect later if the code is changed, often "if the patch is refreshed".
- **`(style)`** — coding-style / formatting / convention. Cosmetic but expected
  to be fixed; phrase as "this isn't a bug, but ...".
- **`(typo)`** — spelling/wording in code, comment, or commit message.
- **`(suggestion)`** — optional related design/improvement idea.
- **`(nit)`** — below `(minor)`: purely cosmetic or illustrative, with no effect
  on behavior even in principle (e.g. a leaked handle or small compile error in
  a man-page *example*). Mention it only so it can ride along on a refresh that
  is happening anyway; it is never a reason to touch the patch.

Don't flood a patch with dozens of nits; prioritize `(defect)` and the
highest-value `(style)` items, and anchor each to its own line.

Keep your positions consistent across patchsets: don't ask for X on one
revision and the opposite on the next. If an earlier round of this review gave
advice that turned out wrong, say so rather than silently reversing.

## Review cycles are expensive — surface minors, never force a refresh for them

Every refresh of a patch costs a full test/CI cycle plus reviewer attention.
That drives how minor findings are handled:

- **Always report the minor things** (`(minor)`, `(style)`, `(typo)`,
  `(suggestion)`, `(nit)`) — people need to be aware of them — but frame each as
  opportunistic: "if the patch is refreshed, ...". They are a free ride on a
  refresh that happens for other reasons, not a reason to refresh.
- **If nothing requires a refresh** (no `(defect)`, no real correctness /
  interop / commit-message problem), do not disturb a patch that has already
  passed testing. Make the verdict say so explicitly, e.g. "Looks good; a few
  optional nits inline for whenever it is next refreshed — no need to re-spin
  for them."
- **If a refresh is needed anyway** (a pressing issue exists), include every
  minor item you found so it can be fixed for free in the same cycle, e.g.
  "Needs a refresh for X; while at it, the inline minors."
- Minor items are **never** the sole basis for a negative verdict.

## Worked example

```json
{
  "tag": "autogenerated:ai-review",
  "message": "Mostly good, comments inline. The new behavior looks untested — consider adding a sanity case that exercises the new flag.",
  "comments": {
    "/COMMIT_MSG": [
      {
        "line": 7,
        "message": "The subject says \"osc:\" but the diff is entirely under lustre/mdc/. Should the component tag be mdc?",
        "unresolved": true
      }
    ],
    "lustre/include/uapi/linux/lustre/lustre_idl.h": [
      {
        "line": 3934,
        "message": "This adds a new on-wire flag; wirecheck.c and both wiretest.c copies don't seem to be updated to match. Should they be?",
        "unresolved": true
      }
    ],
    "lustre/osc/osc_request.c": [
      {
        "line": 1423,
        "message": "If osc_extent_find() returns an error here, is `oap` still freed on the way out, or does this path leak it?\n\n    rc = osc_extent_find(...);\n    if (rc)\n        return rc;   /* oap allocated above */",
        "unresolved": true
      }
    ]
  }
}
```

Note the routing: the overall verdict and the whole-patch "add a test"
observation are in `message`; the commit-message component-tag question is a
`/COMMIT_MSG` line comment; the wire-protocol concern anchors to the real
`lustre_idl.h` line; the leak question anchors to its code line.

## Validity check (mandatory)

After writing `./gerrit-review.json`:
- Confirm it is valid JSON (no trailing commas, all strings escaped). If you can
  run a tool, `python3 -m json.tool ./gerrit-review.json` must succeed.
- Confirm every key under `comments` is a real file path from this patch or the
  `/COMMIT_MSG` magic path — whole-change points anchor to `/COMMIT_MSG`.
- Confirm `message` is the overall verdict (plus any legitimate non-commit-
  message whole-patch observation), not a restatement of the inline comments,
  and that no commit-message matter (Fixes:/subject/body/Test-Parameters) was
  put in `message` instead of `/COMMIT_MSG`.
- Confirm no finding you classified as a false positive made it in.
- Regenerate the file if it is malformed.
